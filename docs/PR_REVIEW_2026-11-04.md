### PR 109: strided metric planes and VMAF frames

[PR 109](https://github.com/imazen/zenmetrics/pull/109), head `739a0aa0`, has
useful exact-parity tests for differing strides, poisoned padding and minimum
buffer extents. It remains draft because the VMAF packed fast path still
constructs temporary normalization vectors unconditionally:

- `VmafV1Scorer::score` calls `tight_frames` for each input and then collects
  both results again into frame-descriptor vectors.
- `VmafV0Scorer::score` uses the same pattern.
- `tight_plane` borrows tightly packed samples, but `tight_frames` still
  collects a `Vec<TightFrame>` even when every plane is already packed.

See [the v1 path](https://github.com/imazen/zenmetrics/blob/739a0aa0810d1aca2b3525b4d3d4b04700b596c7/crates/vmaf/src/score.rs)
and [the v0 path](https://github.com/imazen/zenmetrics/blob/739a0aa0810d1aca2b3525b4d3d4b04700b596c7/crates/vmaf/src/v0_score.rs).
This does not meet the requirement that adding stride support leave the
packed path without extra normalization allocations. Retain a direct packed
route and apply normalization only where needed.

The PR's [timing note](https://github.com/imazen/zenmetrics/blob/739a0aa0810d1aca2b3525b4d3d4b04700b596c7/benchmarks/strided_linear_planes_tight_path_2026-11-03.md)
also reports a packed-path slowdown in its default build. Its forced-alignment
experiment does not qualify the normal build's cost, and the note explicitly
says its harness was not committed. Those historical timing claims were not
independently rerun in this review. Commit a reproducible harness and remeasure
the ordinary build after correcting the packed path. CUDA execution is also
unqualified by the PR's reported local controls.

This is a request to complete the chosen strided API, not to drop stride
support or weaken its parity tests. After the corrections, rebase on current
master and retain the existing tight/strided and warm/cold numerical checks.
