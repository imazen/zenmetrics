## Gate and decision

Replay two already completed cells on each of the two permitted LAN workers under the same image, pinned thread count, and input archive. The result JSON fields `prediction`, `score`, `selected_epoch`, `inner_mean_geomean3_by_epoch`, and selected checkpoint bytes must match the dev originals bit-for-bit. Compare JSON values with exact numeric equality and checkpoint SHA-256 with byte equality; report full-file hashes separately because `selected_bake` paths or receipt paths may vary. A difference fails the gate and requires a diagnosed cause and a single-era grid; rerun all completed cells on the fleet if equality cannot be proved. The potential lane's local runner must be paused by the coordinator's READY/GO handoff before declaring remaining jobs.

The fit manifest includes the SHA-256 of the fit program bundle, the data archive, and canonical argv per cell. These bind the content-addressed job ID. Every output must have a ledger DONE row, a matching content-addressed blob, a result JSON, and an independently checked receipt before harvest. No fit result is a scientific pass by itself; the potential lane's existing `summarize.py` and `check_core_gates.py` own all later statistics and decisions.

The program bundle contains the exact fit executor script as well as the pinned P0 scripts, `zen_stats.py`, three current-main Rust binaries and build metadata. The image installs the executor from this bundle, so changing executor behavior changes `program_sha` and every fit job ID.

## 13:56 UTC runtime-log caveat and single-era rule, before any replay

The original `result.json` embeds `inner[*].log_sha256`, and those training logs contain measured `t=...s` durations at each epoch. The full JSON file hash can therefore differ across hosts even when every fit outcome is byte-identical. The replay gate requires exact equality for predictions, scores, selected epoch, all inner score values and fit/validation counts and bounds, final bounds and row indices/counts, seeds, label/provenance fields, and selected checkpoint bytes. It excludes only the runtime-bearing training-log hash from the inner receipt comparison and reports the complete `result.json` hash separately. Because literal full-JSON byte identity with dev cannot be proved in the presence of runtime durations, **all 960 P0 cells will be run in one current-main fleet era**, including cells already completed on the dev box. No old result will be mixed into the final P0 grid. Any difference in the required outcome fields between the two fleet hosts must be diagnosed and fixed before READY. The potential lane's statistics and selection remain unchanged.

## 2026-09-25 gate outcome and single-era decision (after replay; written by the Claude Sonnet continuation lane)

**Gate as preregistered: FAILS against the dev-box originals, and the cause is the CPU tier, not the transport.**

- Two LAN workers of different microarchitecture (a Zen+ host under the tower's Docker caps, and a Zen2 host) produce bit-identical predictions, scores, selected epochs, inner-fold series and checkpoint weights for both gate cells (`POT_kadid_train_r0_mlp32/o0_r0`, `o1_r1`). The verifier's `a_vs_b` rows fail only the two fields that are diagnostic by design (`full_result_bytes`, `selected_checkpoint_full_file`: runtime-bearing log hashes and the checkpoint's embedded hostname/timestamp trailer).
- Both differ from the dev-box originals. The same pre-rule binary in the same Ubuntu 26.04 image reproduces the dev original exactly on the dev box and reproduces the fleet numbers on the fleet host, and `RAYON_NUM_THREADS` 1/4/8 does not change the fleet numbers. The dev box has AVX-512; `zensim-train-core/src/simd_encoder.rs` selects 16-wide (`X64V4Token`) vs 8-wide (`X64V3Token`) dot-product kernels. Environment masking (`RUST_STD_DETECT_UNSTABLE`) did not disable the AVX-512 path, so a tier cannot be pinned without a code change in zensim, which is outside this lane.
- **Decision (unchanged from the 2026-09-24 amendment, now with evidence):** one era per grid. If the coordinator approves GO, all 960 P0 cells run on non-AVX-512 fleet workers; the 44+ locally completed dev-box cells are not mixed in (they stay as diagnostics). The fleet era's numerics differ from the AVX-512 era at the training-trajectory level (o0_r0, final glibc image: test SROCC 0.9499 fleet vs 0.9504 dev; selected epoch 0 vs 25; per-family permutation importances differ substantially, e.g. `basic` 0.093 vs 0.321). Any comparison across grids or with the potential lane's local P2/permutation grids must state the tier.
- **Amendment to the gate's checkpoint criterion:** `zensim_mlp_train` appends a JSON metadata trailer after the weights, so checkpoints are compared by the weight bytes preceding the trailer.
- **Amendment to the cell definition:** every outer-fold cell also runs `mlp_importance.py` (commit `a450807c8a13`, sha `6d28cdd9ecb1784be7194947e16287531354372436411a4511af0255bfafb559`; `stability_lasso.py` `822ee7c5d023`, sha `8dd081008595780ca49a40fd3e560d286bc9d783cef4c8b6a0e4ab2ab5fc62f2`), as `run_mlp_baseline.sh` does locally, so `importance.json` and `perm_*` files exist for `check_core_gates.py`.
- Cost model: H32 cells 400 s, H128 cells 1600 s (dev box); worker watchdog for fit cells 8 h. Per-cell CI receipts (`ci.json`) remain the potential lane's post-harvest aggregate step (`run_mlp_ci.sh`), not a fleet cell output.
