# PieAPP qualification, 2026-10-16

Status: both native engines pass all 24 numerical pairs and warm/cold checks.
All required individual landing checks pass; wrapper bookkeeping was revalidated
separately after the in-flight source-edit error described below.

The port reconstructs [Prashnani et al., CVPR 2018](https://arxiv.org/abs/1806.02067)
section 3 / figure 4 and official checkpoint tensor metadata. No official
implementation source, pyiqa package or pyiqa weights are read or used.
The independently written reconstruction is exported to ONNX; the official
release is run only as an opaque oracle through `compute_score`.

## Sources and sampling

Official release revision: `0513613d1f575136ea52418e35f2cebc5a49f783`.
[Checkpoint](https://web.ece.ucsb.edu/~ekta/projects/PieAPPv0.1/weights/PieAPPv0.1.pth)
SHA-256: `0937b01480c7a637ae3018af755faa8ecde4788b52bb246b7ae62cf96fb6baf0`.
Weights have modified BSD-2 noncommercial terms and require explicit consent;
no weights are committed.

The [release README](https://github.com/prashnani/PerceptualImageError/blob/master/README.md)
documents dense stride-six 64×64 patches. The canonical convention uses the regular
valid-origin grid, without an extra unaligned far-edge patch, and parity against
the official `compute_score` entry point. Public patch errors/weights are pooled
in f64 row-major order. Graphs take RGB `[0,1]` and convert to BGR code values.
Batches hold at most 32 patch pairs; references cache planar conversion only.

On `1415_128`, the original demo CLI returns `1.6797861082006782`, whereas
`compute_score` on the regular 121-patch grid returns `1.6567797660827637`.
The absolute divergence is `0.0230063421179145` native units. The documented
`--sampling_mode sparse` flag returns `1.7122649515845207`; it does not explain
the dense result. No CLI-wrapper equivalence is claimed. Official source is
not inspected; further wrapper probes are restricted to documented options.

## Oracle runtime controls

The original Python 2.7 / torch 0.3.1 CPU release and the modern
Python 3.12.14 / torch 2.14.1 execution adapters are isolated outside git.
The adapters preserve old scalar shapes/indexing, integral reshape sizes and
contiguous device-copy semantics. CUDA disables TF32 and uses deterministic
cuDNN. Every GPU oracle batch is repeated; a mismatch requires a third matching
result or fails. Native GPU scoring uses the same repeat/third-run policy.

The original CPU control scores are `2.5778071880340576` at `1415_64` and
`1.6567797660827637` at `1415_128`. The modern CUDA oracle with bounded batches
and f64 pooling gives `2.57780671119689941` and `1.65677990440824097`.
Absolute differences: `4.76837158203125e-7` and `1.3832547729464295e-7`.
Resource receipt: run-heavy rc=0, 4s, peak-RSS 1.57 GiB, min-avail 14870 MiB,
peak-load 21.20. These are numerical controls, not throughput benchmarks.

## Reproduction

Heavy commands run serially under the shared flock and `run-heavy --mem 16G
--jobs 16`, with `TMPDIR` on disk and
`LOCK_SNAP_DIR=$HOME/tmp/zenmetrics-lock-snap-pieapp`.

- `just nn-pieapp-export PYTHON CHECKPOINT NEW_MODEL_DIR`
- `just nn-pieapp-entry-oracle ORACLE_PYTHON PAIRS_TSV NEW_SCORES_TSV cuda`
- `just nn-pieapp-score MODEL_DIR PAIRS_TSV NEW_SCORES_TSV ort-cuda`
- `just nn-pieapp-calibration-summary PAIRS_TSV SCORES_TSV NEW_SUMMARY_JSON`
- `just nn-pieapp-gates MODEL_DIR LADDER`

`benchmarks/pieapp_measure_2026-10-16.sh` runs the complete oracle ladder,
native controls and KonJND calibration. Runtime compatibility adapters are
preserved in `crates/zenmetrics-nn/models/pieapp/oracle_runtime_{cpu,cuda}.py`.
Full image/model artifacts and calibration tables remain outside git; final
hashes and compact summaries are linked in the qualification section below.

The supported qualification ladder contains 24 pairs: three sources at
64, 128, 256, 512, 1024 and 2048 square pixels, plus six non-square pairs
(1024×684, 684×1024, 333×448, 448×333, 320×240 and 240×320).
The non-square copies used in the manifest were SHA-256 checked against the
dedicated non-square corpus and match byte for byte. Inputs with either
axis below 64 are explicitly rejected; unit controls cover zero dimensions
and 63-pixel axes before pixel access. No unsupported geometry is silently
skipped by a scoring call.

## Native pilot controls

Against the modern official public-entry-point oracle, native absolute errors:

| Engine | 1415_64 | 1415_128 |
|---|---:|---:|
| ort-cuda | 0 | 1.3950328381362453e-7 |
| rten | 9.5367431640625e-7 | 1.2017119876972515e-7 |

The official identical-patch result is `-3.72529029846191406e-9`; native CUDA
reproduces it exactly. PieAPP identity checks preserve warm/cold bit identity
and compare against this measured oracle using the existing JND tolerance.

The pinned [official README](https://github.com/prashnani/PerceptualImageError/blob/0513613d1f575136ea52418e35f2cebc5a49f783/README.md)
explicitly recommends obtaining patch errors/weights in smaller groups and
combining them to avoid materializing every patch for a large image. This
supports the bounded oracle/port schedule. Its documented sampling option is
`--sampling_mode dense|sparse`; no separate stride option is documented there.

The numeric panel covers 64–2048 square pixels and the six supported
non-square pairs. It does not cover 4096×4096: that geometry exceeds the
declared 9,000,000-pixel bound and is explicitly refused. The supported
contract also requires both axes >=64 (1,048,576 pixels maximum on 32-bit).

now load command text before execution, and calibration installation lives
in a separate Python helper. Real calibration/input-manifest verification
and shell syntax checks were rerun successfully; numerical code did not
change and the completed numeric panels were not repeated for that wrapper fix.
